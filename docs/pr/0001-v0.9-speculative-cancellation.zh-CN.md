# PR 说明：v0.9 首个有效候选胜出与 speculative solver 取消

## 为什么做

长程代码 Agent 不应该在某个 speculative solver lane 已经返回协议合法候选后，仍然无条件
等待所有 lane。之前的有界并发已经可审计、可恢复，但始终会等满整个 width。

## 改动内容

- 新增 `OrchestrationConfig.speculative_solver_stop_on_valid` 以及对应 CLI 参数
  `--speculative-solver-stop-on-valid`。
- 第一个通过 `parse_proposal_response` 的响应成为 durable winner。
- 对尚未完成的 lane 发起本地 task cancellation，并写入 hash-chain 事件
  `solver.speculative.winner` / `solver.speculative.cancelled`。
- provider-specific adapter 可以实现可选的 `request_cancellation(request)` hook；事件会记录
  `acknowledged`、`not_observed`、`unsupported` 或 `failed:*`，但不会把本地 task cancellation 包装成远端
  exactly-once abort。
- checkpoint 恢复时，如果已经有落账且协议合法的 lane，会直接复用它，不再启动缺失的
  speculative 请求。
- 报告增加 `speculative_winners`、`cancelled_solver_lanes`、winner/cancelled lane 明细，
  并保留按配置 width 计费的预算口径。
- 增加确定性测试：lane 2 阻塞，lane 1 返回后触发胜出和取消。

## 验证

```text
python -m unittest tests.test_orchestrator -v
python scripts/ci_checks.py
python -m unittest discover -s tests -q
```

## 结论边界

这里的“valid”只表示严格的候选 JSON/快照协议解析成功，不表示通过 visible/hidden test。
最终是否接受仍由统一可见测试 oracle 和 reviewer gate 决定。取消明确是
`best_effort`：取消本地 asyncio task 不能保证 provider 已经停止远端 HTTP 请求。
solver/model 预算仍按配置的 width 计数，真实成本节省需要 provider-aware adapter 单独测量。
默认串行 OpenAI-compatible adapter 可以关闭活动的本地 HTTP response 并返回
`acknowledged`；但 Chat Completions 没有标准远端 abort endpoint，因此该状态不能证明
服务端生成已经停止。
