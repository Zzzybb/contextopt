# v0.8 代码 Agent 策略评测补充说明

## 改了什么

本说明记录 PR #1 中加入的 v0.8 评测层：

- `contextopt.evaluation.agent_search` 增加两个可执行 fixture：ACM 风格 Two Sum
  修复题、扩展欧几里得算法修复题，并为每题配置不进入模型快照的独立 grader；
- `agent-eval` 在统一的轮数、模型调用、候选数和测试预算下比较
  `single_pass`、`best_of_n`、`orchestrated`，并在可见测试通过后记录 hidden grader；
- JSON 和 Markdown 输出完整 run ledger 以及可校验的汇总指标；
- 测试覆盖 fixture 完整性、可见测试 oracle 信号、报告 round-trip、篡改检测、配置
  校验和离线 CLI。
- 顺序编排中的三个角色现在会把各自 assistant 历史交给共享的 ContextCompiler；每个
  RoleCall 和角色事件都会保存 ContextReceipt、编译后消息哈希以及版本化观察记忆指纹。

默认实现使用 `ScriptedModel`，但可见测试和 hidden grader 都会在临时工作区中由真实
测试进程执行，因此候选计数和 oracle gate 不是伪造的，也不需要 API key。CLI 也支持
OpenAI-compatible 模型做固定 fixture 的探索性运行，每个矩阵单元都会创建新的 adapter。

## 为什么改

角色编排可以证明 planner/solver/reviewer 的状态机是可持久化的，但一段角色对话
本身不能证明它有价值。这个 harness 把三种面试中容易解释的代码 Agent 控制策略
放到同一组算法/数学题上，记录每种策略真正消耗的调用、测试和 token，既能解释
Best-of-N 与 retry loop 的成本，也为未来接入真实模型保留了稳定接口。

## 如何复现

~~~text
python -m contextopt agent-eval \
  --fixtures all --repetitions 1 \
  --output agent-eval.json --markdown agent-eval.md

python -m unittest tests.test_agent_search_eval -v
~~~

当前默认离线矩阵的结果是：故意较弱的 `single_pass` 基线 0/2，`best_of_n` 2/2，
`orchestrated` 2/2。完整 accounting 保存在生成的 JSON 中，Markdown 适合放到 PR
或作品集展示。

## 指标和边界

主要指标包括可见测试 `success_rate`、条件式 `hidden_success_rate`、模型/角色调用
均值、候选数、实际可见/隐藏测试进程、缓存复用、轮数以及 provider 报告的 token 用量。
失败运行会保留在 ledger 中。即使弱基线失败，只要评测矩阵完整执行，命令仍返回 0，
因为失败本身就是数据。

脚本模式是固定响应下的控制策略和协议指标；真实模型模式会记录 provider 用量和
hidden grader，但仍只是固定小样本探索性运行。两种模式都不能解释为通用模型能力、
延迟、provider 稳定性、安全隔离或生产编码成功率。fixture 通过不代表真实模型一定
能发现相同算法。

角色 receipt 的边界也很明确：它只能证明本轮选择了哪些 transcript block、使用了哪一
版观察记忆，不能证明模型理解或有效利用了每个 block。跨运行学习型语义记忆仍不在本
版本范围内。
