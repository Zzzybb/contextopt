# v0.8 bounded parallel scheduler addendum

## Scope

This follow-up adds the first executable multi-agent scheduling primitive without weakening the
existing oracle boundary:

- `SearchSessionConfig.max_parallel_tests` and `OrchestrationConfig.max_parallel_tests` bound
  concurrent candidate evaluations;
- every candidate is materialized by the existing trusted executor in its own temporary
  workspace, so candidates cannot share files or mutate the model-visible root snapshot;
- scheduler events record candidate requests and completions in deterministic candidate order;
- session and orchestration checkpoints persist observations after each completed result and
  record `max_in_flight`, allowing recovery to reuse durable results and rerun only the missing
  observations;
- CLI and Markdown/console reports expose the configured and observed parallelism.

## Evidence

The new session and orchestration tests run four independent candidates with a two-worker
budget, assert an observed maximum in-flight count of two, verify four requested/completed
events, and compare the final checkpoint with the in-memory report. Existing serial tests keep
`max_parallel_tests=1` as the deterministic baseline.

```text
python -m unittest tests.test_search_session tests.test_orchestrator -v
python -m unittest discover -s tests -q
python scripts/ci_checks.py
```

## Claim boundary

This is bounded parallel oracle execution, not adaptive PatchTree/MCTS scheduling, speculative
model calls, merge-aware workspaces, or an OS sandbox. A candidate test process is trusted host
code. Completion events provide at-least-once recovery semantics: a process that dies after a
subprocess finishes but before its checkpoint is atomically replaced may rerun that candidate.
