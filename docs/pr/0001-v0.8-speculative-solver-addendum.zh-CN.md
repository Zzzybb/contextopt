# v0.8 PR 补充：有界 speculative solver 并发

## 本次改动

- 新增 `OrchestrationConfig.speculative_solver_width` 和 CLI 参数
  `--speculative-solver-width`，默认值为 `1`。
- 当宽度大于 1 时，为每个 lane 构造带多样性指令的 solver 请求，在共享模型/solver 预算内
  并发等待 provider。
- 每个 lane 独立校验。合法的完整快照会先 namespace，再统一进入可选
  `merge_policy=disjoint` 和 visible-test oracle；格式错误或 provider 失败保留为 lane 级
  证据，不会丢掉其他成功 lane。
- `OrchestrationRound.solver_variants`、`pending_solver_variants`、lane 事件、请求/响应哈希、
  ContextReceipt、token 用量和 `max_provider_in_flight` 会进入 JSON、Markdown、HTML 报告，
  可以审计实际并发而不是只看配置。
- 宽度为 1 时保留原有确定性脚本行为和候选 id。

## 验证

- `python scripts/ci_checks.py`
- `python -m unittest discover -s tests -q`
- 新增离线延迟 ScriptedModel 测试，验证两个 solver await 确实重叠、调用数正确、快照被
  namespace，并且 checkpoint 可以精确往返。

## 边界

这只是有界并发，不是通用分布式调度器。planner 和 reviewer 仍然顺序调用；如果进程在
provider fan-out 中断，恢复可能重试整个 lane 组，不声称 exactly-once。真实 provider 的
重复实验仍需要 API key，在此之前不能把离线脚本结果当成模型能力结论。
