# v0.8 PR addendum: bounded speculative solver calls

## What changed

- Added `OrchestrationConfig.speculative_solver_width` and the CLI flag
  `--speculative-solver-width` (default `1`).
- A width greater than one builds lane-specific solver requests and awaits the provider calls
  concurrently under the shared model and solver budgets.
- Each lane is validated independently. Valid complete snapshots are namespaced before they are
  combined, merged (when `merge_policy=disjoint` is enabled), and sent to the same visible-test
  oracle. A malformed response or provider failure is retained as lane-local evidence instead of
  discarding successful lanes.
- `OrchestrationRound.solver_variants`, `pending_solver_variants`, lane events, request/response
  hashes, context receipts, token usage, and `max_provider_in_flight` make the fan-out auditable
  in JSON, Markdown, and HTML reports.
- The default width of one preserves deterministic scripted runs and existing candidate ids.

## Verification

- `python scripts/ci_checks.py`
- `python -m unittest discover -s tests -q`
- Added an offline delayed ScriptedModel test that asserts two solver awaits overlap, two lane
  calls are counted, snapshots are namespaced, and the checkpoint round-trips exactly.

## Boundary

This is bounded concurrency, not a general distributed scheduler. Planner and reviewer calls are
still sequential. If a process stops while the provider fan-out is in flight, resuming can retry
the whole lane group; no exactly-once provider claim is made. Real-provider repetitions still
require an API key and must be run before making model-quality claims.
