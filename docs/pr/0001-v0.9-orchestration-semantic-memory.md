# PR #1 — v0.9 semantic memory in multi-agent orchestration

## Why

The durable-memory candidate path previously covered the single-agent runtime and its
provider-free evaluator, while planner/solver/reviewer orchestration only used observed
memory. This change makes the knowledge-base boundary useful to the multi-agent path too.

## What changed

- `OrchestrationRunner` and `run_orchestration` accept an optional
  `SemanticMemoryStore` and scope.
- `orchestrate` accepts `--memory-store`, `--memory-scope`, and
  `--context-memory versioned-v1+semantic`.
- Planner, solver (including speculative lanes), and reviewer requests compile bounded
  durable candidates through the same `ContextCompiler` while keeping role histories isolated.
- A pending role request replays the persisted receipt snapshot after a live-store mutation;
  it does not silently switch candidate sets.
- Added integration tests for all-role projection and pending solver replay, plus bilingual
  documentation.

## Claim boundary

The store remains a lexical, advisory notebook. This proves candidate projection, budget
accounting, provenance, and replay behavior; it does not prove that a provider understood or
used a memory, or that coding success improved.
