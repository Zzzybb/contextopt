# PR note: v0.9 first-valid speculative solver cancellation

## Why

Long-running coding agents should not wait for every speculative solver lane when one lane has
already produced a protocol-valid candidate. The previous bounded fan-out was auditable and
resumable, but it always waited for the full width.

## What changed

- Added `OrchestrationConfig.speculative_solver_stop_on_valid` and the matching
  `--speculative-solver-stop-on-valid` CLI flag.
- The first response that passes `parse_proposal_response` becomes the durable winner.
- Unfinished lanes receive local task-cancellation requests and produce hash-chained
  `solver.speculative.winner` / `solver.speculative.cancelled` events.
- Checkpoint resume can recognize a previously durable valid lane and avoid starting missing
  speculative calls.
- Reports expose `speculative_winners`, `cancelled_solver_lanes`, winner/cancelled lane details,
  and the configured-width budget accounting.
- Added a deterministic cancellation test where lane two blocks until the first lane wins.

## Verification

```text
python -m unittest tests.test_orchestrator -v
python scripts/ci_checks.py
python -m unittest discover -s tests -q
```

## Claim boundary

“Valid” means the strict candidate JSON/snapshot protocol parsed successfully; it does not mean
the candidate passed visible or hidden tests. The common visible-test oracle and reviewer gate
still decide acceptance. Cancellation is explicitly `best_effort`: cancelling a local asyncio
task cannot guarantee that every provider stopped a remote HTTP request. Solver/model budgets
charge the configured width, so cost savings must be measured by a provider-aware adapter.
