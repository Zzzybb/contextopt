# v0.8 evaluation dashboard addendum

## Scope

This follow-up adds a reviewable visualization surface for the coding-agent evaluation
without changing the evaluation protocol or its claim boundary:

- `render_agent_evaluation_html(report)` renders a dependency-free, self-contained HTML
  dashboard from the same `AgentEvalReport` used by the console and Markdown renderers;
- the dashboard shows visible and conditional hidden success bars, strategy-level cost
  columns (`mean_model_calls`, `mean_test_calls`, and `mean_total_tokens`), and the claim
  boundary next to the result;
- the complete serializable report is embedded in a collapsible JSON ledger, so a reviewer
  can inspect the underlying fixture/strategy/repetition records without trusting a chart;
- `agent-eval --html PATH` writes the dashboard alongside the existing JSON and Markdown
  artifacts; omitting the flag preserves the previous CLI behavior;
- README, runtime/evaluation docs, and this bilingual PR note document the portfolio/PR
  workflow and the fact that real-model runs remain exploratory.

## Why

The evaluation already records the accounting needed for an Agent engineering discussion,
but a raw JSON file hides the relationship between quality and cost. A static artifact makes
the same run easy to review in a browser or attach to a pull request while keeping the JSON
ledger as the source of truth. There are no external JavaScript or CSS dependencies, network
requests, or new scoring rules.

## Evidence

The renderer test checks the visible/hidden legend, strategy table, claim boundary, and
embedded durable payload. The CLI test writes all three formats through the public command:

```text
python -m unittest tests.test_agent_search_eval -v
python -m ruff check src tests
python -m mypy src/contextopt
python -m unittest discover -s tests -q
python scripts/ci_checks.py
```

## Claim boundary

The dashboard is a presentation layer, not a benchmark. It does not improve model quality,
hide failed baseline runs, or turn deterministic fixtures into evidence of generalization,
latency, provider reliability, or production safety. Hidden success remains conditional on
visible acceptance, and real-provider repetitions still require fixed model/version,
prompt, fixture, tool, and budget controls before making a comparison.
