# PR #1 — v0.9 terminal semantic-memory feedback loop

## What changed

- Added an opt-in `OrchestrationConfig.memory_feedback` flag and the matching
  `orchestrate --memory-feedback` CLI switch.
- At terminal orchestration, collect only durable-memory candidates that were actually selected
  by planner, solver, or reviewer context receipts. An accepted run records `helpful`; an
  exhausted or failed run records `not_helpful`.
- Use a deterministic `run_id`/`memory_id` feedback key and append a `memory.feedback` event to
  the orchestration hash chain. Reopening a terminal checkpoint therefore reuses the same
  idempotent store operation instead of counting a second vote.
- Record invalidated or unknown candidates as `skipped` audit events without changing the coding
  result. Console/Markdown metrics expose `memory_feedback_events`.

## Claim boundary

This is a durable, idempotent outcome-correlation signal for later lexical ranking. It does not
prove that a memory caused a patch to succeed, does not perform automatic memory consolidation,
and does not measure real-provider coding quality. The feature is opt-in and has no effect on
legacy non-semantic runs.
