# PR note: v1.0 matched model-matrix analysis

## Why

The real-provider workflow produces one report and manifest per run. Comparing those files by
hand makes it easy to pool different fixture sets, budgets, source revisions, or sandbox
policies and then call the result a model comparison. The collection path needs a separate,
strict analysis step before any cross-model claim is made.

## What changed

- Add `agent-eval-compare`, which consumes repeated `REPORT MANIFEST` bundles with explicit
  labels and refuses protocol drift using a canonical SHA-256 fingerprint.
- Validate that each manifest matches its report config, adapter, repository revision, runtime
  limits, sandbox, and container image before pooling anything.
- Preserve per-model strategy summaries and paired deltas, then add model-level direction
  counts, means, and observed variance for cross-model consistency.
- Write JSON, Markdown, and self-contained HTML analysis artifacts without copying raw
  provider credentials or ledgers into the aggregate.

## Validation

```text
python scripts/ci_checks.py
python -m unittest tests.test_model_matrix
```

Example:

```text
python -m contextopt agent-eval-compare \
  --bundle model-a artifacts/model-a.json artifacts/model-a.manifest.json \
  --bundle model-b artifacts/model-b.json artifacts/model-b.manifest.json \
  --output model-matrix.json --markdown model-matrix.md --html model-matrix.html
```

## Claim boundary

This is a matched-artifact guard and descriptive generalization summary. It does not pool raw
cells across incompatible experiments, fit a random-effects model, correct for multiple
comparisons, or prove general coding ability. Real-provider collection, independent hidden
tests, fixed prompts/tools/budgets, and at least three repetitions remain prerequisites for a
credible exploratory comparison.
