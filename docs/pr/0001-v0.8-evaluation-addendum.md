# v0.8 coding-agent strategy evaluation addendum

## What changed

This addendum records the v0.8 evaluation layer added to PR #1:

- `contextopt.evaluation.agent_search` defines two executable coding fixtures, each with
  a model-hidden independent grader:
  an ACM-style Two Sum repair and an extended Euclidean algorithm repair;
- `agent-eval` compares `single_pass`, `best_of_n`, and `orchestrated` under paired
  round/model/candidate/test budgets, then records hidden-grader outcomes after visible
  acceptance;
- JSON and Markdown renderers expose the complete run ledger and self-consistent summaries;
- tests cover fixture completeness, visible-oracle signal, report round trips, tampering,
  configuration validation, and the offline CLI path.
- The sequential roles now compile assistant-only history through the shared ContextCompiler;
  each RoleCall and role event persists a ContextReceipt with the compiled-message hash and
  versioned observed-memory fingerprint.

The default implementation uses `ScriptedModel` responses. The visible and hidden test
commands are real processes in disposable temporary workspaces, so candidate accounting
and oracle gates are exercised without requiring an API key. The CLI also accepts an
OpenAI-compatible model for exploratory fixed-fixture runs, with fresh adapters per cell.

## Why

The role orchestrator proved that planner/solver/reviewer state can be durable, but a role
transcript alone does not demonstrate value. This harness puts three recognizable coding-
Agent control policies on the same small algorithm/math tasks and records what each policy
actually spends. It gives an interview-ready explanation of why Best-of-N and retry loops
cost more calls/tests, and provides a stable seam for later real-model adapters.

## Reproduce

```text
python -m contextopt agent-eval \
  --fixtures all --repetitions 1 \
  --output agent-eval.json --markdown agent-eval.md

python -m unittest tests.test_agent_search_eval -v
```

The default offline matrix currently reports 0/2 for the deliberately weak `single_pass`
baseline, 2/2 for `best_of_n`, and 2/2 for `orchestrated`. The exact accounting is stored
in the generated JSON; the Markdown file is intended for a PR or portfolio artifact.

## Metrics and claim boundary

The primary metrics are visible-test `success_rate`, conditional hidden-grader
`hidden_success_rate`, mean model/role calls, candidate proposals, actual visible and
hidden test processes, cached test reuses, rounds, and provider-reported token usage. The
ledger preserves failed runs. A completed command exits zero even when a weak baseline
fails, because that failure is an evaluation observation.

Scripted mode is a deterministic control-policy and protocol measurement. Provider mode
records actual usage and hidden-grader outcomes but remains an exploratory fixed-fixture
run. Neither mode measures general model capability, latency, provider reliability,
security isolation, or production coding success. A passing fixture is not a claim that a
real provider would discover the same algorithm.

The role receipts are also deliberately bounded in their claim: they prove which transcript
blocks were selected and which observed-memory version was used, not that a model understood
or productively used every selected block. Learned cross-run semantic memory is still out of
scope.
