# v0.9 follow-up — opt-in semantic-memory context candidates

## Summary

The durable memory store was previously available only through an explicit `memory_search`
tool call. This follow-up adds a bounded, opt-in projection for coding-agent runs so useful
cross-run experience can participate in normal context routing without becoming mandatory prompt
text or an unaudited side channel.

## Changes

- Add `versioned-v1+semantic` to the single-agent context policy. When an attached
  `SemanticMemoryStore` is present, the runner retrieves at most three lexical matches for the
  current task; `--memory-scope` optionally narrows the project scope while retaining `global`.
- Render matches as labelled advisory assistant blocks. They are ordinary context candidates with
  confidence, matched-term, tag, and freshness signals, so `submodular`, `density`, `topk`, and
  `recent` routing can select or evict them under the existing estimated-token budget.
- Extend `ContextFrame.metadata` with candidate ids, selected ids, full serialized match
  snapshots, and the durable-store fingerprint. The combined memory fingerprint covers both the
  per-run observed ledger and the durable store view.
- Teach recovery and pending-request resume to rebuild candidates from the receipt snapshot. A
  process can stop, the live store can change, and the pending request still replays the exact
  candidate messages whose request hash was recorded.
- Keep the default `versioned-v1` behavior unchanged: semantic memory remains explicit unless the
  caller opts into the new policy.

## Claim boundary

This is bounded context plumbing, not a learned retriever or proof that memory improves coding
success. Retrieval remains provider-free lexical matching; candidate text is advisory and must be
verified against current workspace evidence. The receipt proves which candidates were available
and selected, not that a model used them correctly.
