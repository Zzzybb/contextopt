# PR note: v1.0 opt-in Docker candidate sandbox

## Why

Host process cleanup and credential scrubbing reduce accidental leaks, but they are not an OS
security boundary. Controlled real-model coding evaluation needs a repeatable way to run visible
and hidden candidate graders outside the host filesystem and network.

## What changed

- Add `ExecutableSearchConfig(sandbox="docker", container_image=...)` and matching CLI flags to
  branch search, search sessions, orchestration, and `agent-eval`.
- Run the candidate command with Docker `--network=none`, `--read-only`, `--cap-drop=ALL`,
  `--security-opt=no-new-privileges`, `--pids-limit`, bounded memory/CPU, a small `/tmp` tmpfs,
  and a single writable `/workspace` bind mount.
- Use `python` inside the container rather than the host's absolute interpreter path for the
  ACM/math visible and hidden graders.
- Add a unique container name and force-remove it after timeout; the host process-group/Windows
  Job Object cleanup remains the outer lifecycle guard.
- Persist sandbox/image identity in execution and evaluation checkpoints so resume cannot silently
  switch execution boundaries.

## Validation

```text
python -m unittest tests.test_branch_executor tests.test_agent_search_eval -v
python scripts/ci_checks.py
```

The local development host does not have Docker, so the local suite validates the explicit
configuration and missing-runtime failure path. The GitHub Actions `docker-sandbox` job runs the
same adapter against `python:3.12-slim` on a Docker-enabled Ubuntu runner and fails if the container
path cannot execute a candidate.

## Claim boundary

This is an opt-in controlled execution path, not a guarantee that every deployment is secure.
The operator must pin and review the image, Docker daemon, mount policy, and host runner. The
default remains a trusted host process; no real provider benchmark is claimed by provider-free CI.
